# TIER 2 of the log scan: KNOWN, UNRESOLVED findings. These are NOT accepted as normal.
# Format: ID <TAB> ERE <TAB> STATUS <TAB> summary (with a pointer to the evidence).
# A kernel-log line that matches an entry is reported as XLIN-TEST: logscan finding-<ID> FINDING
# in every boot where it appears. A run with a FINDING is not "clean": the host judge reports
# PASS WITH OPEN FINDINGS, lists the finding (with how many boots showed it) in every summary,
# and `xlin-runtime-test --strict-findings` turns it into a failing exit status.
# An entry is removed only by a reviewed decision recorded in docs/RUNTIME-VALIDATION.md;
# the scanner is never relaxed to make a finding disappear.
# STATUS is one of: OPEN (not yet reviewed to a conclusion) | EXPLAINED-OPEN (cause identified,
# but the residual risk or the upstream/Arch comparison is not closed) | EXPLAINED-UPSTREAM (the
# upstream kernel developers have analysed and consciously kept this exact message; reviewed decision
# recorded in docs/RUNTIME-VALIDATION.md. Still reported as a FINDING, never accepted as normal, never
# a clean pass; our own verification is stated separately from upstream's assessment).
W-X-CPA-ITS	CPA detected W\^X violation	EXPLAINED-UPSTREAM	kernel 6.18.64 x86 CPA W^X check (verify_rwx, pr_warn_once before rodata is read-only) fires for the ITS mitigation thunk page: its_alloc() calls set_memory_x() on a still-writable page during alternative_instructions(), made ROX again by its_fini_core(); only on CPUs where "ITS: Mitigation: Aligned branch/return thunks" is active. Final mappings checked clean by CONFIG_DEBUG_WX in the same boots. Host/VMM-dependent: 578 of 578 boots on the Intel Xeon 6975P-C CI class under QEMU 8.2.2, none on other hosts, and none for the same kernel under QEMU 11. The Arch linux-lts kernel (6.18.65-1) under the same QEMU 8.2.2, host class and job shows the same ITS message and notice in 80 of 80 boots, so it is upstream behaviour, not an Xlin configuration effect; that does not show it is harmless. Upstream already analysed this exact line: mainline commit ea6fd393cb9e (2026-09-13, "x86/mm/pat: Use pr_warn() for early W^X warnings", Closes lore.kernel.org/all/20260905044253.GA3816371@ax162) attributes it to its_alloc() set_memory_x() during early retpoline setup and calls the window temporary and not a transient security issue, keeping a quiet warning. The same behaviour was measured on 6.18.65 and mainline 7.4.0-rc4 (40 of 40 boots each, same host class and QEMU). Reclassified EXPLAINED-UPSTREAM by reviewed decision (2026-11-25): the cause and the harmlessness assessment are upstream's (ea6fd393cb9e); NOT verified by us: the caller was not traced in our guests, exploitability and upstream's claim that all kernel text is RWX at that moment were not tested, the enhanced-IBRS link is inferred, only one host class with QEMU 8.2.2/11.1.3 and no bare metal was covered. No upstream report is being sent; the draft is an internal research record. See docs/RUNTIME-VALIDATION.md, "Open finding: CPA W^X"
XTILE-CPUID	XFEATURE_XTILE_DATA: calculated size is|CPUID\[0d, [0-9a-f]+\]: eax=	EXPLAINED-OPEN	kernel 6.18.64 check_xtile_data_against_struct() (arch/x86/kernel/fpu/xstate.c) prints this error, followed by a dump of CPUID leaf 0xd, when guest CPUID leaf 0x1d (AMX tile palette) reports no palette (calculated 0 bytes) while leaf 0xd advertises 8192 bytes of AMX tile data. The kernel ignores the result and still enables AMX. Seen on the CI host class Intel XEON PLATINUM 8573C (43 of 43 boots, 2026-11-23/24; also Arch linux-lts 6.18.64-1 under QEMU 11.1.3 in run 45167768437) and in 1 TCG boot (earlier counts 1 of 56 here and 1 of 136 in the runtime document, not reconciled; not explained by the mechanism below); never on the other hosts. Forced mechanism REPRODUCED (research branch research/xtile-cpuid, commit cce518c; docs/XTILE-CPUID-INVESTIGATION.md): when the guest advertises AMX-TILE but its maximum CPUID leaf is 0x1c, a query for leaf 0x1d returns leaf 0x1c data (empty); on AMX-capable Xeon 6975P-C/6973P-C hosts -cpu host,level=0x1c fired in 212 of 212 boots (Xlin 6.18.64, vanilla 6.18.65, mainline 8d7fe9885c62, Arch linux-lts; QEMU 8.2.2 and 11.1.3), level>=0x1d or AMX off in 0 of the others (counts parsed from CI logs, lower bounds). Tested AMX works, including in guests where the check fires: arch_prctl permission, tile config/zero/store and a TDPBSSD int8 multiply (the multiply only in run 45618759770). Supports a VMM-layer explanation; responsibility among hypervisor, QEMU and the kernel's missing max-leaf validation is NOT assigned. NOT established: the original failing 8573C runners did not reproduce (all 3 sampled on 2026-11-25 exposed no AMX, level 0x1c, did not fire), so their historical host state is not directly established; untested AMX functionality (bf16/fp16, context switch, signals, ptrace, XFD with threads, load, performance, bare metal). Investigation not closed.
