# TIER 2 of the log scan: KNOWN, UNRESOLVED findings. These are NOT accepted as normal.
# Format: ID <TAB> ERE <TAB> STATUS <TAB> summary (with a pointer to the evidence).
# A kernel-log line that matches an entry is reported as XLIN-TEST: logscan finding-<ID> FINDING
# in every boot where it appears. A run with a FINDING is not "clean": the host judge reports
# PASS WITH OPEN FINDINGS, lists the finding (with how many boots showed it) in every summary,
# and `xlin-runtime-test --strict-findings` turns it into a failing exit status.
# An entry is removed only by a reviewed decision recorded in docs/RUNTIME-VALIDATION.md;
# the scanner is never relaxed to make a finding disappear.
# STATUS is one of: OPEN (not yet reviewed to a conclusion) | EXPLAINED-OPEN (cause identified,
# but the residual risk or the upstream/Arch comparison is not closed).
W-X-CPA-ITS	CPA detected W\^X violation	EXPLAINED-OPEN	kernel 6.18.64 x86 CPA W^X check (verify_rwx, pr_warn_once before rodata is read-only) fires for the ITS mitigation thunk page: its_alloc() calls set_memory_x() on a still-writable page during alternative_instructions(), made ROX again by its_fini_core(); only on CPUs where "ITS: Mitigation: Aligned branch/return thunks" is active. Final mappings checked clean by CONFIG_DEBUG_WX in the same boots. Host/VMM-dependent: 578 of 578 boots on the Intel Xeon 6975P-C CI class under QEMU 8.2.2, none on other hosts, and none for the same kernel under QEMU 11. The Arch linux-lts kernel (6.18.65-1) under the same QEMU 8.2.2, host class and job shows the same ITS message and notice in 80 of 80 boots, so it is upstream behaviour, not an Xlin configuration effect; that does not show it is harmless. Upstream already analysed this exact line: mainline commit ea6fd393cb9e (2026-09-13, "x86/mm/pat: Use pr_warn() for early W^X warnings", Closes lore.kernel.org/all/20260905044253.GA3816371@ax162) attributes it to its_alloc() set_memory_x() during early retpoline setup and calls the window temporary and not a transient security issue, keeping a quiet warning. The same behaviour was measured on 6.18.65 and mainline 7.4.0-rc4 (40 of 40 boots each, same host class and QEMU). Exploitability not tested by us; kept open pending a reviewed decision. See docs/RUNTIME-VALIDATION.md, "Open finding: CPA W^X"
XTILE-CPUID	XFEATURE_XTILE_DATA: calculated size is|CPUID\[0d, [0-9a-f]+\]: eax=	EXPLAINED-OPEN	kernel 6.18.64 check_xtile_data_against_struct() (arch/x86/kernel/fpu/xstate.c) prints this error, followed by a dump of CPUID leaf 0xd, when the guest CPUID leaf 0x1d (AMX tile palette) reports no palette (calculated 0 bytes) while leaf 0xd advertises 8192 bytes of AMX tile data. The kernel ignores the result and still enables AMX ("Supporting XSAVE feature 0x40000"). Seen on the CI host class "Intel XEON PLATINUM 8573C" (43 of 43 boots) and in 1 of 56 TCG boots; never on the other hosts. Not diagnosed whether QEMU/KVM or the host kernel withholds leaf 0x1d. See docs/RUNTIME-VALIDATION.md, "Open finding: XTILE-CPUID"
